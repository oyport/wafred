トンネルは、プライベートネットワーク内のサービス（NAS、社内アプリ、データベースの管理画面）を、**受信ポートを開けず、そのホストに公開 IP も持たせず**に公開します。コネクタは外向きにエッジへ接続し、エッジが公開側を終端します。WAF の保護（ルール、レート制限、チャレンジ、キャッシュ、アクセス制御、ログ、証明書、オリジンへの TLS）はそのまま適用されます。エッジにとってトンネルは通常のオリジンだからです。

## 構成要素

| 要素 | 動作する場所 | 役割 |
| --- | --- | --- |
| **コネクタ**（`wafred-tunnel`） | プライベートネットワーク内 | コントロールプレーンとエッジへ**外向きのみ**接続し、各接続を内部ターゲットへ転送 |
| **エッジのリスナー** | WAF エッジ（`tunnel_addr`、ポート `9443`） | コネクタの TLS セッションを受け、ターゲットごとにループバックブリッジを開く |
| **ブリッジ** | エッジ上の `127.0.0.1:<一時ポート>` | プロキシから見てトンネルを通常のオリジンにする |
| **オリジンプールの紐付け** | コントロールプレーン | サイトのトラフィックがこのトンネル経由で到達できる内部 `host:port` を指定 |

トンネルは VPN ではありません。紐付けたオリジンプールのトラフィックだけを運びます。1 つのトンネルは 1 つの信頼ドメインです。

## 三つの状態を区別する

| 状態 | 意味 |
| --- | --- |
| **ペアリング済み** | 資格情報が存在し、利用可能 |
| **有効** | 運用者によるトンネル単位のスイッチ |
| **コネクタがオンライン** | 現在コネクタが制御ストリームを保持している |

「ペアリング済み＋有効」でコネクタがオフライン、というのは正常な構成です。

## 五つの手順

### 1. トンネルを作成する

**エージェント → トンネル → Create tunnel**。コンソールがワンタイムのペアリングコマンドを表示します。トークンは**一度だけ**表示され、既定で 30 分後に失効します。再発行すると資格情報がローテーションされ、稼働中のコネクタは切断されます。

### 2. 内部ホストでコネクタを動かす

```bash
sudo wafred-tunnel pair \
  --config /etc/wafred/tunnel.toml \
  --server-url https://control-plane:9090 \
  --server-ca-cert /etc/wafred/tunnel-ca.pem \
  --token <pairing-token>
sudo wafred-tunnel run --config /etc/wafred/tunnel.toml
```

`pair` はトークンを長期資格情報と交換し、`/etc/wafred/tunnel.toml`（`0600`）を書き出します。`run` はコントロールプレーンへの制御ストリームと、エッジごとのセッションを維持します。どちらにも到達できない場合は `warn` でログが出ます。

### 3. エッジのリスナーを有効にし、公開アドレスを与える

```toml
[agent]
tunnel_addr = "0.0.0.0:9443"
```

ファイアウォールで `9443` を許可し、**エージェント → [ノード] → トンネルイングレス** に公開 `host:port` を入力します。エッジは初回起動時に自己署名証明書を生成して保持し、SHA-256 を報告します。コネクタはそれをピン留めします。リスナーは起動時にバインドされるため、`tunnel_addr` の変更にはエッジの再起動が必要です。イングレスアドレスとポリシーは反映が速く、接続済みなら 5 秒以内に届きます。

### 4. オリジンプールを紐付ける

**サイト → [サイト] → オリジンプール → [プール] → トンネル**。プールのノードアドレスがコネクタの接続先になります。セッションがない間、そのプールに送られるリクエストは既定のオリジンへフォールバックせず `503` を返します。

### 5. 動作を確認する

1. **コネクタがオンライン** — 一覧のバッジと詳細パネルの「エッジ」。`wafred-tunnel status` でも同じ状態を確認できます。
2. **エッジがイングレスを提供** — 詳細パネルにエッジとターゲットが表示される。
3. **サイトが応答する** — サイトの Host で `curl -H 'Host: app.example.com' --resolve …` を実行し、`200` を確認します。

## リクエストの流れ

クライアント → エッジ `:443` → WAF パイプライン → トンネルに紐付いたプール → ループバックブリッジ → TLS 多重化セッション → コネクタ → 内部ターゲット。アクセスログではオリジンが `tunnel://<名前>/<ターゲット>` と表示されます。

## 直接の外向き接続がない場合（SOCKS5）

```toml
socks5_proxy    = "10.0.0.1:1080"
socks5_username = "connector"
socks5_password = "…"
```

制御プレーンのストリームとエッジへの全セッションがプロキシ経由になります。ターゲット名はプロキシ側で解決され（ATYP 3）、直接接続への暗黙のフォールバックはありません。

## 運用

| 操作 | 効果 |
| --- | --- |
| **再ペアリング** | 資格情報をローテーションし、稼働中のコネクタを切断 |
| **失効** | 資格情報を削除。エッジは次のバンドル（5 秒以内）で拒否 |
| **無効化** | トンネル単位のスイッチ。次回リロードでセッションを閉じる |
| **削除** | プールが参照している間は `409`。`?force=true` で紐付けを解除し、プールは**直接**オリジンに戻る |
| **設定** | デプロイ全体のスイッチ、トークン寿命、セッションあたりのストリーム数など |

## セキュリティモデル

エッジはコネクタの資格情報を見ません。コントロールプレーンが Ed25519 で署名した**短命のセッショントークン**を検証するだけです（鍵は `jwt_secret` から導出）。取得されたトークンは既定 1 時間で失効し、他のトンネルには使えません。コネクタはエッジ証明書をピン留めし、不一致なら失敗します。失効はエッジがコントロールプレーンに到達できる間は次のリロードで反映されます。

## トラブルシュート

| 症状 | 確認 |
| --- | --- |
| `cannot reach the control plane` | `server_url`、`9090`、CA、SOCKS5 プロキシ |
| オンラインなのに「エッジ 0」 | エッジの `tunnel_addr` またはイングレスアドレス未設定 |
| 資格情報が拒否される | トークンの失効、またはエッジが新しい公開鍵を受け取っていない |
| サイトが `502/503` | セッションがない、またはコネクタがターゲットに到達できない |
| 削除が `409` | プールが参照中。解除するか `?force=true` |

## このバージョンの制限

サイト経由の HTTP/HTTPS/WebSocket のみ（生 TCP は未対応）。1 トンネル＝1 信頼ドメイン。ターゲット数とストリーム数は設定で上限があります。
