# WAFred 1.0.4 基准测试与修复报告

测试日期：2026-11-22  
语料：`chaitin/blazehttp`，commit `afc88a94d03db1cd52156c34c3c9c58053c9f658`  
范围：全量攻击/正常请求回放、固定漏报/误报回归、gzip 请求体、自签证书 HTTPS 和原部署容量数据复核

## 结论摘要

- 原始漏报统计受到回放器 framing 错误影响：不少带请求体的语料没有 `Content-Length`/`Transfer-Encoding`，回放器却按原始字节发送，实际服务器按无请求体处理。修正回放器后，严格档请求体检查全量拦截为 **632/658（96.05%）**，正常请求受影响 **19/33,219（0.057%）**。
- 另外 15 条正常样本的实际字节数超过它们声明的 `Content-Length`，代理拒绝额外数据并返回 HTTP 500。修正回放器以声明长度截断后，四档全量测试的 HTTP 500 均为 0；这不是 WAF 的 15 条误拦截。
- 对原始 WAFred 二进制使用同一修正回放器做 Strict 与 Strict + body 对照：候选分别新增拦截 1 条和 2 条攻击，没有丢失已有命中，也没有增加正常样本误拦或质询。
- 完成四档各 33,877 条全量回放、四档 gzip 套件、自签证书 HTTPS 和 20 条漏报/27 条误报固定集。HTTP 与 HTTPS 的规则探针均按预期返回。
- `.64` 上现有 all-in-one 生产进程 PID 25940 未停止、修改或替换。候选构建仅在隔离进程中测试，尚未部署。

## 漏拦截归因与修复

### 回放器没有正确描述请求体

BlazeHTTP 原始夹具中有请求体但未携带 framing 头的样本。原 `replay.py` 未补齐长度，直接写 socket；HTTP/1.1 服务端因此把请求解释为没有请求体。攻击载荷没有进入 WAF 请求体检测，这类样本此前被记作“WAF 漏报”，其实是测试夹具没有把载荷作为请求体发送。

回放器现有如下规则：

- 非空请求体缺少 `Content-Length` 和 `Transfer-Encoding` 时，按实际字节数补 `Content-Length`。
- 存在且只有一个语法有效的 `Content-Length` 时，丢弃其后多出的字节。本回放器每条 TCP 连接只发送一个请求，因此这些字节不是另一条需保留的流水线请求。
- 多个/非法 `Content-Length` 和 `Transfer-Encoding` 用例保持原样，用于协议层测试。

此外，15 条正常夹具在合法 `Content-Length` 之后还附加了尾字节。旧回放器把它们发给上游后触发 `Sent data after end of body`，WAF 返回 500，而同一请求体按声明长度直连模拟源站返回 200。截断 framing 外的字节后，四个档位的 15 个 500 全部消失。

### WAF 归一化和规则缺口

- 未声明 `Content-Type` 的表单正文此前作为一个弱类型整体扫描，单个高风险字段可能达不到 Strict 评分阈值。现在仅对具备明确 `key=value` 或 multipart boundary/`Content-Disposition` 结构的正文进行有界字段解析。
- 对 Base64 编码的独立 URI 路径段，整条路径前导 `/` 会令整值 Base64 解码失败。现在在长度上限内逐段解码并加入普通规则扫描。
- Strict 新增关键级 `alert.call(` 和 `prompt.call(` 签名，便于将单个已解码 JavaScript 调用判为高风险；规则在 Normal 档不装配。

针对根因加了回归测试：未声明类型的 URL-encoded/multipart 表单、Base64 路径段、无害表单、HTTP body framing 和 `Content-Length` 尾字节。回放器单元测试 4/4 通过。`cargo test -p wafred-waf` 为 271/271 通过，`cargo fmt --all -- --check` 通过。

## 全量语料测试

共 33,877 条：恶意 `.black` 658 条，正常 `.white` 33,219 条。拦截率按 403 与 503 质询合计；误报按正常请求的 403/503 合计。表中时延是端到端语料回放值。

| 档位 | 攻击拦截 | 正常请求受影响 | p50 / p95 | 回放错误 | HTTP 405 | HTTP 500 |
|---|---:|---:|---:|---:|---:|---:|
| Normal | 397/658（60.33%） | 4/33,219（0.012%） | 43 / 48 ms | 0 | 1 | 0 |
| Normal + body | 494/658（75.08%） | 12/33,219（0.036%） | 43 / 48 ms | 0 | 1 | 0 |
| Strict | 501/658（76.14%；491 拦截、10 质询） | 4/33,219（0.012%） | 43 / 48 ms | 0 | 1 | 0 |
| Strict + body | **632/658（96.05%；622 拦截、10 质询）** | **19/33,219（0.057%）** | 43 / 48 ms | 0 | 1 | 0 |

每档各有一条 `CUST` 自定义方法请求返回 405，模拟源站也返回 501；它是方法层兼容性差异，不是规则命中。Strict + body 的 19 条正常样本受影响包括 17 条拦截、2 条质询。27 条 pinned 正常样本复测仍是 17 拦截、2 质询、8 放行，与全量集受影响项相同。受影响数按类别为：`other` 5（3 拦截、2 质询）、RCE 5、XSS 3、LFI 3、SQLi 1、CRLF 1、SSTI 1。

### 同一 framing 下的旧二进制对照

为隔离回放器修复与 WAF 规则变化，旧二进制和候选二进制用同一份修正回放器、同一 Strict + body 配置、同一 33,877 条样本运行，再按样本逐项比较：

| 档位 | 原二进制命中 | 修复候选命中 | 攻击新命中 | 丢失命中 | 新增正常拦截/质询 |
|---|---:|---:|---:|---:|---:|
| Strict | 500/658 | 501/658 | 1 | 0 | 0 |
| Strict + body | 630/658 | 632/658 | 2 | 0 | 0 |

Strict 档新增命中是编码 `other` 路径样本；Strict + body 额外拦截了一条 SQLi 样本。逐项 diff 显示除此之外三万余条样本 verdict 不变。此对照显示请求 framing 修复提升了旧版本的测量准确性；WAF 代码变化在统一的修正输入上增加攻击命中，没有扩大本次语料误报。

### 修复后仍未拦截的请求

Strict + body 中剩余 26 条没有得到 403/503：23 条得到 200、2 条被 HTTP 解析器以 400 拒绝、1 条自定义方法返回 405。20 条固定漏报集中抽样集里，1 条已由候选规则拦截，18 条放行，另 1 条返回 405。剩余放行样本包括多层编码、应用专用管理/探测路径、超长截断 URI，以及可见输入缺少通用恶意信号的样本；例如部分 XSS 标签样本含空参数或只含普通锚点标记，XXE 样本使用空 SYSTEM 标识符和未声明实体。

剩余样本仍作为固定漏报集，逐条确定应用语境和误报代价后再加规则。不要用覆盖整个管理路径、空参数或通用字符串的宽泛签名补齐百分比。

## 容量结果与限制

以下网络压测来自原部署二进制 `2b3842ec…`，并非源代码修复候选。256 并发、Strict + body、2 KiB POST、3 分钟 soak 完成 931,266 个请求（5,172 RPS），HTTP 200 全部成功、连接错误 0、RSS 峰值 113.5 MiB。该轮未见持续 RSS 增长，但不足以替代长时间 soak。

512 并发时原部署进程软 `nofile=1,024`：Normal GET 出现 30 个 502，Strict + body POST 出现 68 个 502；日志显示 `Too many open files`。隔离副本将软限制设为 65,536 后均无 502。没有修改生产进程/服务单元。由于本轮修复了请求体归一化，候选构建的高并发 soak 仍须单独补测。

本轮安全矩阵为 HTTP/1.1 和模拟源站；HTTPS 测的是 WAF 入口。真实业务源站、HTTP/2/HTTP/3、多站点生产路由、限速/CC、WAF 到源站 TLS 和修复候选的长时间/高并发 soak 尚未覆盖。WAFred 行是 2026-11-22 本地候选全量复测；SafeLine 等行使用不同样本口径和环境，只作历史参考。
